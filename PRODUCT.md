# Product

## Register

product

## Users

The primary user is the local operator running Project Telos outreach from the `C:\dev` workspace. The operator is working through a multi-lane public outreach queue and needs dense, accountable state for drafts, confirmation gates, artifacts, target URLs, follow-ups, and execution receipts.

Secondary users are future assistant sessions that must orient from files and command output rather than memory. They need the workspace to expose source-of-truth context, not raw private session histories.

## Product Purpose

This workspace supports local-first Project Telos execution: mapping repositories, preparing public proof-surface artifacts, staging outreach, tracking confirmation gates, and recording external actions only after operator-confirmed execution.

Success means the operator can move from context to packet to confirmation to ledger without losing evidence boundaries, leaking private paths, or turning unsupported claims into public copy.

## Brand Personality

Direct, careful, and evidence-led. The product voice is pragmatic and human: it should feel like a precise operations console for work that may become public, not like a marketing surface.

## Anti-references

Do not make this look like a landing page, sales funnel, launch splash, decorative SaaS dashboard, or hype wall. Avoid ornate visuals, oversized hero sections, bloated cards, gradient-heavy decoration, and any UI that slows the operator down.

Do not make public-facing copy sound like certification, compliance, endorsement, or model-safety overclaiming.

## Design Principles

1. Evidence before action: every public action must connect to a source file, copy block, confirmation phrase, and ledger record.
2. Dense but readable: show queue state compactly without burying the operator in prose.
3. Public-safe by default: surface gates, placeholders, and non-claims before any external write.
4. File state beats memory: dashboards and consoles should read generated queue artifacts, not rely on session recollection.
5. The summary is not the record: the UI should make records, packets, receipts, and unresolved states visible.

## Accessibility & Inclusion

Target WCAG AA contrast for operator-facing text and controls. Use familiar product UI affordances, keyboard-reachable links and buttons, visible focus states, restrained motion, and responsive layouts that preserve table usability on small screens.
